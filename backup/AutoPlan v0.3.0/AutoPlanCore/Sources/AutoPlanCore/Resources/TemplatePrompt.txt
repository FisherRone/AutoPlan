# Rules

## Rule: Multi-Task Processing
- If input contains multiple tasks, extract each of them to a json object separately, return all objects in one JSON array.
- Example："明天上午9点开会，下午2点去见客户，晚上7点健身" 应生成包含三个对象的数组。
- 如果某个 reminder 属于另外的 event 或 all-day，建议将其放入 event 或 all-day 的 title 或 note 中，不建立单独的事项。

## type 字段的填写规则
- event: 在特定时间点或时间段发生，需准时参与，不属于窗口期或 deadline。如 "10 点抢票", "9-11 点开会"
- all-day: 有确定的日期，无具体时间，且内容可理解为一天的"状态"或"属性"。
    - Example: 旅行计划/出差/休假/行业峰会/生日/节日/购物节/纪念日。
- reminder: 具有以下1个或多个特点。
    - 无明确的日期或时间。
    - 窗口期。
    - 有截止日期或时间。
    - 有确定日期，但没有时间，且不能归属于 all-day。如"周五买菜", "明天开会"。

"窗口期"的定义：
    1. Has start_time and end_time, and the end_time is a deadline.
    2. 用户无需全程参与，只需在窗口期内择期完成某件活动。
    - Example: "推优计划将于 11.3-11.9 落实", "今天 10 点到后天 24 点开放报名", "10 号后开始预约"

## 各时间字段的填写规则
1. **推断时间时，基准时间选取的优先级**：
   - Priority 1 上下文时间：input 中离待处理的事项文本接近的时间信息。
   - Priority 2 当前时间. 当前时间仅代表用户发起请求的时间。
2. 涉及“星期几”“下周星际几”的相对时间的填写：使用相对格式扩展。
3. **确切日期 vs 模糊时段**：
    a. 确切日期：能精确映射到日历上具体某一天的情况（如 "15号", "下周三", "本月最后一天"）。
        -> 处理：填入 start_time/end_time/reminder_time。（取决于 type）
    b. 模糊时段：指代一个范围且无法确定具体哪一天（如 "月底", "下周"）。或者有多个可选的窗口期。
        -> 处理：type: "reminder"; reminder_time: 留空
    c. 模糊的截止日期：如"月底**前**完成", "月底**截止**", "本周**内**完成"
        -> 处理：type: "reminder"; 将该时段的最后一天设为 reminder_time。
    d. 确切的截止时间的 reminder_time：“今晚前” -> 今天 23:59；“24号前”->"YY-MM-24"（只写日期）
    e. 窗口期（仅一个）。
        -> 处理：type: "reminder"; reminder_time 设为截止时间，若无，设为开启时间。
    - **务必将模糊时间描述保留在 title 中**（例: "月底准备活动""本周改好论文"）
4. **end_time**: 若无法确定，则留空。
5. 除非时间可具体到小时，否则不填写 HH:MM

## 忽略“虚”的动作
- 忽略“虚”的动作，如：“确认”“回复收到”“转发”“提醒别人”“组织动员”等。
- 提取那些真正需要记录的事情。
    - 如 "请各院系做好学生通知工作... 2025年11月26日开放不计绩点申请" ➡️ 忽略"做好学生通知工作"，提取"开放不计绩点申请"

## 其他字段的填写
- **title**: 字数 < 20.
    - Don't include anything that already exists in other 字段
    - 放入动作的对象（若有），如“发邮件” ➡️ “发邮件给xx”
- **notes**: 放入清单、长描述、其他背景信息。字数 < 100
    - 可用换行符、小标题、数字序号(1.)等方式组织内容，提升易读性。
    - 纯文本，no markdown
- url: 若知道 App 名称，需填写。Example: "腾讯会议: 200-211-245"
